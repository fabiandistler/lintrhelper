### 1. `na-1` — Descendant-Achse macht `require_function_arguments()` still blind

- **Datei:Zeile:** `R/high_level_linters.R:303` — `named_args <- xml2::xml_find_all(call_expr, ".//SYMBOL_SUB")`
- **Ausloesender Input:** Beliebige gelintete Quelle, in der ein *verschachtelter* Aufruf das geforderte Argument traegt. Gemessen mit `require_function_arguments("data.frame", "stringsAsFactors")` auf `data.frame(a = read.csv(f, stringsAsFactors = FALSE))` -> 0 Lints statt 1; ebenso `out <- data.frame(id = 1, value = as.character(read.table(p, stringsAsFactors = FALSE)[[1]]))` -> 0.
- **Auswirkung:** Falsch-negativ ohne jedes Signal — kein Fehler, keine Warnung, kein Lint. `.//` sammelt jeden `SYMBOL_SUB` im Teilbaum, `%in%` (Zeile 307) kann Herkunft nicht unterscheiden, `Filter()` verwirft den verletzenden Aufruf, bevor `xml_nodes_to_lints()` (Zeile 310) ihn sieht. Betroffen ist genau das dokumentierte Beispielmuster der Funktion (Zeilen 256-270, im README beworben) bei gewoehnlichem R-Code. Wer den Linter in seine `.lintr` haengt, glaubt die Regel sei durchgesetzt.
- **Mechanismus festgenagelt:** Am selben `call_expr` liefert `.//SYMBOL_SUB` -> `a,stringsAsFactors`, `./SYMBOL_SUB` -> `a`. Kontrollen: `read.csv(f, header = TRUE)` -> 1 Lint, `read.csv(f)` -> 1 Lint (anders benanntes verschachteltes Argument maskiert nicht).
- **Schweregrad:** hoch (Impact-Skeptiker korrigiert auf mittel, siehe unten)
- **Kostet der Fix etwas? Nein, geprueft:** `tests/testthat/test-high_level_linters.R:142-163` deckt ausschliesslich *flache* Aufrufe ab (`data.frame(x = 1:3)` mit und ohne Argument). Kein Bestandstest haengt an einem verschachtelten Fall, den die Kind-Achse kippen wuerde. Positionelle Uebergabe und partielles Matching (`stringsAsFact = FALSE`) erzeugen entweder gar keinen `SYMBOL_SUB` oder einen mit abweichendem Text und werden von beiden Achsen gleich behandelt — der Fix aendert also genau den verschachtelten Fall und sonst nichts.
- **Fix-Skizze:** Kind-Achse `./SYMBOL_SUB` statt `.//SYMBOL_SUB`; benannte Argumente sind direkte Kinder des Aufruf-`<expr>`. Beide Kontrollfaelle als Regressionstests festschreiben — der Bestandstest `tests/testthat/test-high_level_linters.R:142-164` deckt nur flache Aufrufe.
- **Repro:** ausgefuehrt, von allen drei Linsen unabhaengig reproduziert.

### 2. `api-1` — Linten fuehrt fremden Code aus: `read_only_hint = TRUE` ist falsch, und dessen Ausgabe bricht das MCP-stdio-Framing

> **Achtung, hier stecken zwei Befunde mit sehr verschiedener Reichweite in einem.**
> Wer nur nach Schweregrad triagiert, fixt die stdout-Senke und uebersieht den zweiten.
>
> **(a) Unbedingt wahr, ohne jede Zusatzbedingung:** `read_only_hint = TRUE` in
> `R/mcp_tools.R:42` (`lint_file`) und `R/mcp_tools.R:82` (`lint_project`) ist eine
> falsche Zusage. `object_usage_linter` laedt die Namespaces der gelinteten Pakete,
> und `.onLoad`/`.onAttach` fremden Codes laeuft dabei im Serverprozess. Das Tool ist
> nicht read-only, es fuehrt beliebigen Code aus. MCP-Clients nutzen dieses Flag, um
> Tools ohne Rueckfrage laufen zu lassen — die Korrektur dieser zwei Zeilen ist der
> billigste und am breitesten wirksame Teil des ganzen Audits.
>
> **(b) Bedingt:** Schreibt so ein `.onLoad` auf stdout, landet Nicht-JSON im
> Frame-Strom (Details und Reichweiten-Einschraenkung unten).

- **Datei:Zeile:** `R/mcp_tools.R:214` (`lint_file`), identisch `R/mcp_tools.R:371-372` (`lint_whole_project` ueber `lintr::lint_package`)
- **Ausloesender Input:** Installiertes Paket `polluter` auf `.libPaths()` mit `R/zzz.R`: `.onLoad <- function(libname, pkgname) cat("POLLUTION-FROM-ONLOAD\n")` und einer Datei mit undefiniertem Symbol. Server per `Rscript --no-init-file --no-site-file -e 'lintrhelper::start_mcp_server()'`, danach `tools/call` mit `{"name":"lint_file","arguments":{"path":"R/f.R","project_dir":"<scratch>/polluter"}}`. Beobachtetes stdout: Zeile 1 = initialize-Result, **Zeile 2 = `POLLUTION-FROM-ONLOAD` (kein JSON)**, Zeile 3 = tools/call-Result; stderr leer. Gleiches Leck ueber `lint_project`.
- **Auswirkung:** `object_usage_linter` (Tag `default`, laeuft ohne `.lintr`) ruft `lintr:::make_check_env()` -> `try_silently(getNamespace(pkg_name))`; `try_silently` faengt Conditions, aber kein `cat()` auf fd 1 — demselben fd, auf den mcptools die JSON-RPC-Frames legt. Eine Nicht-JSON-Zeile steht damit *innerhalb* des Frame-Stroms, nachweislich nach dem Handshake. Der geschriebene Satz in `R/mcp_server.R:23-24` ("This package writes only JSON-RPC to stdout", Ausnahme nur `.Rprofile`/`Rprofile.site`, also vor dem Handshake) ist damit falsifiziert. - **Reichweite ehrlich:** Es braucht ein *installiertes* Paket, dessen `.onLoad` (oder das einer Abhaengigkeit) via `cat()`/`print()`/`writeLines(stdout())` schreibt — ein Verstoss gegen die `packageStartupMessage()`-Konvention, kein Normalfall. Kontrollauf gegen das echte Repo: stdout = 2 Zeilen, beide JSON, stderr leer. Ein Verbindungsabbruch wurde **nicht** beobachtet (Server beantwortete die Folgeanfrage, `EXIT=0`); ob ein Client abbricht, ist clientabhaengig und ungeprueft.
- **Schweregrad:** kritisch (Impact-Skeptiker korrigiert auf mittel)
- **Fix-Skizze:** stdout um beide `lintr`-Aufrufe umleiten und Aufgefangenes auf stderr nachreichen (`noise <- utils::capture.output(lints <- lintr::lint(...)); if (length(noise)) message(...)` bzw. `withr::with_output_sink()`). Achtung: `sink()`/`capture.output()` fangen nur R-Connections, Subprozess-Ausgabe aus `.onLoad` braucht fd-Ebene. Zusage in `R/mcp_server.R:23-24` entsprechend einschraenken, `read_only_hint` korrigieren.
- **Repro:** ausgefuehrt, end-to-end gegen den echten Server, in allen drei Linsen.

## Kandidaten fuer CI-Regeln

Nur benannt, nicht gebaut — jedes Muster ist durch mindestens einen bestaetigten Befund belegt:

1. **Descendant-Achse in Linter-Code** (`na-1`): `xml2::xml_find_all(<call_expr>, ".//...")` dort flaggen, wo die eigene Argumentliste eines Aufrufs gemeint ist. Grep-tauglich als `xml_find_all\([^,]+,\s*"\.//` in `R/`, mit Whitelist fuer bewusste Teilbaum-Suchen.
2. **`read.dcf()` ohne BOM-tolerante Connection** (`locale-1`): jeder `read.dcf(<pfad>` ohne `file(..., encoding = "UTF-8-BOM")` als Treffer.
3. **`lintr::lint*()`-Aufruf auf dem Serve-Pfad ohne Ausgabeumleitung** (`api-1`): Aufrufe von `lintr::lint`/`lint_dir`/`lint_package` in `R/mcp_tools.R`, die nicht von `capture.output()`/`withr::with_output_sink()` umschlossen sind.
4. **MCP-Toolargument ohne Normalisierer** (`api-2`): jedes im `inputSchema` deklarierte Argument muss vor Gebrauch durch eine `normalise_*()`-Funktion laufen, die Fehlform mit `stop()` ablehnt — aktuell erfuellen das `tags`, `changed_only` und `rule_name`, aber nicht `dir`/`project_dir`.
5. **Guard-Muster `length(x) != 1L` im `||`-Kurzschluss** (`api-2`): Bedingungen, die eine Fehlform still in einen Fallback leiten statt zu melden — als Review-Regel fuer alle Argument-Aufloeser.
6. **Testabdeckung fuer verschachtelte Aufrufe** (`na-1`): Linter-Tests, die ausschliesslich flache Aufrufe pruefen, als Coverage-Luecke markieren.

Zweitens: der Constraint, unter dem der Fall ueberhaupt entsteht, ist ein Aufrufer, der explizit NULL/NA schreibt, obwohl der Parameter bei R/high_level_linters.R:341 den funktionierenden Default `max_length = 80` traegt. Die vom Befund behauptete realistische Quelle (getOption("myproject.line_length") bzw. cfg$max_length) hat im Repo keine Entsprechung: es gibt keinerlei Konfigurations-Plumbing, das max_length aus einer Option oder Liste zieht - README.md:417 (`limit_line_length(80)()`) und tests/testthat/test-high_level_linters.R:169 (`limit_line_length(10)`) uebergeben Literale, und R/mcp_tools.R konstruiert diesen Linter ueberhaupt nie, der MCP-Konsument erreicht den Pfad also nicht ueber JSON-Parameter. Drittens bricht das Kernargument des Befunds - die Asymmetrie zu `max_length = "80"`, die belegen soll, 'der Konstruktor validiert, nur eben nicht die stillen Faelle' - inhaltlich zusammen: der Abbruch bei "80" ist eine beilaeufige Nebenwirkung des %d-Formatstrings in sprintf() (Meldung: invalid format '%d'; use format %s for character objects), kein absichtlicher Guard. Aus einem Formatierungsunfall laesst sich kein Validierungsvertrag ableiten, den die NULL-Faelle verletzen wuerden. Ich behaupte ausdruecklich keinen existierenden Guard - es gibt keinen; widerlegt ist die Auswirkung, nicht der Mechanismus. Restrisiko und korrigierter Schweregrad: hoechstens 'niedrig/kosmetisch' - ein Entwicklerwerkzeug ohne Nutzdaten und Persistenz, in dem ein explizit hingeschriebenes NULL genau so wirkt wie im Referenzpaket.
