## Befunde

### 1 - `lintr::attach_linter()` existiert nicht  (im PR behoben)

`README.md:321` und `vignettes/getting-started.Rmd:188` empfehlen beide, statt eines
eigenen Linters `lintr::attach_linter()` zu nehmen. Diese Funktion gibt es in lintr nicht.

```
lintr: 3.4.0
lintr::attach_linter exists: FALSE
  in available_linters(): FALSE
lintr::attach_linter() -> ERROR: object 'attach_linter' not found
```

`DESCRIPTION` fordert `lintr (>= 3.0.0)`; in der heute aufgeloesten Version 3.4.0 ist der
Name in keiner der 117 Eintraege von `available_linters()` enthalten.

### 2 - `lintr::sapply_linter()` existiert nicht  (im PR behoben)

Gleiche Stelle, gleiches Muster: `README.md:324`, `vignettes/getting-started.Rmd:191`.

```
lintr::sapply_linter exists: FALSE
  in available_linters(): FALSE
lintr::sapply_linter() -> ERROR: object 'sapply_linter' not found
```

**Was stattdessen stimmt.** Beide Faelle deckt lintr ueber
`undesirable_function_linter()` ab - `attach` und `sapply` stehen in
`lintr::default_undesirable_functions`. Gegenprobe ausgefuehrt:

```

sapply in default_undesirable_functions: TRUE

file.R:1:1: style: [undesirable_function_linter] Avoid undesirable function "attach".
  As an alternative, use roxygen2's @importFrom statement in packages, or `::` in
  scripts. attach() modifies the global search path.
attach(mtcars)
^~~~~~
file.R:2:6: style: [undesirable_function_linter] Avoid undesirable function "sapply".
  As an alternative, use vapply() with an appropriate `FUN.VALUE=` argument to obtain
  type-stable simplification.
y <- sapply(1:3, function(i) i)
     ^~~~~~
```

Befund 1 und 2 sind zu **einem** Listeneintrag bzw. **einer** Codezeile
zusammengefasst worden - zweimal derselbe Linter waere in einer Fuenf-Punkte-Liste
Rauschen.

### 3 - Dokumentierte `quick_test()`-Ausgabe stimmt nicht  (in #54 behoben)

`README.md:459` zeigt als Beispielausgabe:

```
# <text>:1:6: warning: [temp_test_linter] Found match
```

Tatsaechlich ausgefuehrt kommt:

```
<text>:1:6: warning: [temp_linter] Found match
x <- T
     ^
```

**Nicht** auf `[temp_linter]` umgeschrieben, sondern auf `...` gekuerzt - so, wie es das
zweite `quick_test()`-Beispiel im selben Block schon macht. Grund: `temp_linter` ist der
Name einer *lokalen Variablen im Rumpf von* `quick_test()` (`R/testing_utils.R:116`).
Ihn im README festzuschreiben, koppelt oeffentliche Doku an ein internes Detail, das bei
jeder Umbenennung und bei einer Behebung von Befund 4 wieder falsch waere.

### 4 - `linter_name` wird von drei exportierten Buildern ignoriert  (nur Report)

Ursache hinter Befund 3, und der Grund, warum dort gekuerzt statt umbenannt wurde.

Drei exportierte Funktionen nehmen ein Argument `linter_name` entgegen:

| Funktion | Signatur | Weitergabe |
|---|---|---|
| `create_simple_linter()` | `R/simple_linter.R:113` | `R/simple_linter.R:118` |
| `create_function_call_linter()` | `R/simple_linter.R:148` | `R/simple_linter.R:160` |
| `create_assignment_linter()` | `R/simple_linter.R:189` | `R/simple_linter.R:209` |

Alle drei rufen `create_linter_factory(xpath, message, type, ...)` auf.
`create_linter_factory()` (`R/simple_linter.R:1`) hat ueberhaupt keinen Parameter
`linter_name`. Das Argument wird also entgegengenommen und stillschweigend verworfen; der
angezeigte Linter-Name stammt aus lintrs Deparse des uebergebenen Objekts.

Die roxygen-Doku behauptet das Gegenteil - `R/simple_linter.R:92`:

> `@param linter_name A character string naming the linter (used for the lint type).`

Das ist Doku-Drift, aber **nicht doku-seitig behebbar**: den Satz abzuschwaechen wuerde
den Fehler segnen statt ihn zu melden, und `man/` in einen reinen Doku-PR ziehen.
`references/jobs.md` ist an dieser Stelle eindeutig - ein Code-Fix zur Rettung der Doku
ist eine Verhaltensaenderung, der Befund wandert in den Report. Hier gemeldet, im PR
nicht angefasst.

Betroffen sind auch die internen Aufrufer `R/high_level_linters.R:58` und `:238`, die
`linter_name =` ebenfalls setzen.

### 5 - 12 nicht aufloesbare roxygen-Links  (nur Report)

Stand als Backlog-Eintrag in `ROOMBA.md`, ausdruecklich diesem Job zugewiesen
("gehoert aber in Job 2"), aufgefallen im Lauf `deps-audit` 2026-09-01. Hier
zunaechst umgestellt, per Review aber reverted - siehe unten. Der Eintrag wandert
zurueck ins Backlog.

`roxygen2::roxygenise()` meldete 12 Warnungen, alle in `R/mcp_tools.R`:

| Ziel | Fundstellen im Quelltext | Gemeldete Positionen |
|---|---|---|
| `lint_project()` | 222, 246, 253, 361, 419 | 222, 246, 253, 360, 419 |
| `lint_file()` | 151, 274 | 151, 273 |
| `list_rules()` | 529, 682, 687 | 529, 676, 676 |
| `explain_rule()` | 649 | 649 |
| `tool_payload()` | 301 | 277 |

12 Fundstellen, 12 Warnungen, eins zu eins. Die beiden Spalten stehen auseinander, weil
roxygen die Position des *Blocks* meldet, nicht die der Zeile: die Links in 682 und 687
liegen im selben `@details`-Block, den roxygen beide Male als `mcp_tools.R:676` ausgibt.

Die Ursache ist nicht ein Tippfehler, sondern die Paketgrenze: alle fuenf Ziele sind
**intern**, stehen nicht in `NAMESPACE` und bekommen wegen `@noRd` keine Rd-Seite. Ein
`[fn()]`-Link kann deshalb nirgendwo hinzeigen.

Zunaechst behoben durch Umstellung von Link auf Code-Auszeichnung, `[fn()]` ->
`` `fn()` ``, an allen 12 Stellen - `roxygen2::roxygenise()` meldete danach **0**
Warnungen (vorher 12), `git status` zeigte **keine** Aenderung unter `man/`.

Per Review reverted: `[fn()]` ist roxygens Markdown-Link-Konvention und bleibt stehen.
Die Umstellung haette die Link-Absicht getilgt statt die Warnung an der Wurzel zu
beheben. `[ellmer::ContentToolResult()]` loest auf, weil `ellmer` eine deklarierte
Abhaengigkeit ist; die 12 Warnungen auf interne `@noRd`-Ziele bleiben bestehen und
wandern zurueck ins Backlog.
